# Port plan: replay gram's history as a native Rust + macroquad app

## Why

gram began as devbox's `www/svg/ActSvg*`, became act.svg, and then gram-www. It is a browser SVG diagram editor: JS, plus a PHP server for books and pages. The goal is a native Rust + macroquad app that:

- draws the shapes itself, and still reads and writes `.svg` files on disk;
- opens a folder from the command line (`gram ~/diagram_root`) and shows its `.svg` files as an IDE-style tree, instead of flat book/page dropdowns;
- hands text editing to a real editor such as emacs, the way git does;
- is built the everkeep way: bash snippets print Rust, assembled with orc (see `CLAUDE.md`).

The port replays every gram/act.svg commit in date order, starting from devbox's first `www/svg` commit. That includes branches that never reached main: the v0.2 button-bar branch, v0.3 and v0.4. Each commit's added or changed tests are ported into Rust at the step where they appeared.

`CLAUDE.md` holds the lasting rules: the model, the external editor, the folder tree, and the per-step method. This file holds the steps and progress.

## Method for each step

1. **Read** the commit: `git -C history/<repo> show <hash>`, plus `doc/changelog`, `doc/changetask/<CT#>` and `doc/changeboard` when present. For devbox, add `-- www/svg`.
2. **Tests first.** Port every `TDD TEST N` the diff adds or changes into `tests/<area>.test.sh` as `#[test] fn tdd_NN_<slug>`. Drive the mouse, keys and frames through stubbed macroquad functions, as in everkeep's `tests/drag-select.test.sh`. Assert on the model and on the serialized SVG string; "stroke is editColor" becomes a check on selection state and the serialized color. Subtract the JS frame offset `(750, 88)` from the JS `clientX`/`clientY` values.
3. **Implement** or change snippets until `./test.sh` passes.
4. **Mutants.** Turn each `// TDDTEST N FTR` or `FIX` marker into a `tests/mutate.sh` mutant. This replaces the JS `test/test` toggle list (`5 35 57 58 75 76 77 78 80 81 82 83 84`).
5. **Commit:** `replay <repo>@<hash> (<date>): <subject>`, with a body listing the tests ported, what was skipped and any deviation. Tick the step below.

**Paired and unpaired commits.** Almost every gram commit is paired: it matches one historical commit, or a group of them, and uses the `replay` message. A few steps have no historical match because the browser did the work for free, such as parsing and drawing SVG. Those are unpaired steps (`unpaired` in the table). They use the message `prep: <what>` and do only what the next paired step needs. Step 0 (scaffold) and step 2 (render) are unpaired. Add another only when a paired step can't be done without it, and add it to the table first.

Steps with no JS tests still get a Rust test when they add behavior, such as a load/save round-trip, a tree scan or an editor round-trip.

Merge commits are only checked for conflict resolutions; the actual changes are ported at their original commits. Web-only work is skipped: PHP, login, iframe `postMessage`, URL params, JS bundling (saxophone, fast-xml-parser, browserify), nightwatch, playwright and Selenium plumbing.

## Target layout

```
build.sh  test.sh  orc-env.sh
src/main.sh        the app: window, frame loop, wiring
src/models.sh      Node, Doc, Selection, Mode, colors, canvas size
src/*.sh           snippets, added as the replay reaches them:
                   svg-load, svg-save, draw-doc, hit-test, issue-click,
                   select, rect-select, move, snap, map, vertex-resize,
                   clipboard, editor, text-pane, tree, save
tests/*.test.sh    generated into tests/*.rs
tests/mutate.sh
```

Crates: `macroquad`, `quick-xml` and `rstar`, plus a clipboard crate if macroquad's clipboard isn't enough (step 30). Text uses the bundled `assets/LiberationSerif-Regular.ttf` (SIL OFL, `assets/Liberation-LICENSE.txt`), which has Times New Roman's metrics. The old app's CSS set Courier New on the page body, but the diagrams' boxes and the `StartEndFrame.FromText` widths (narrow `i`/`l`/`t`, wide `H`/`W`) were sized for a proportional serif font, which is how a browser shows the `.svg` files. Liberation Mono overflowed the boxes.

## Decisions log

Record here any conflict between a later step and an earlier branch-only feature, along with how it was resolved.

- Steps 0–2 (pre-parity): the canvas goes beyond the browser with an infinite canvas, adaptive grid and R-tree. Hit-testing at step 3 should query the R-tree, then apply the JS ordering (`sortedSvgNodes`: text first, swimlanes and classes last).
- From step 3: a bug in the old code that a later step fixes (a `// TDDTEST N FIX` marker) is written correctly when its code is first ported, not reproduced. At the FIX step, port the JS test and add a "bug" mutant that puts the old bug back. So step 4's `smartMap` (rect→text writing `points`, circle→rect falling through, rect→rect giving NaN, polyline→polyline using the x change for y) is ported as `history/act.svg/js/node-map.js` has it, and steps 5, 6, TDDTEST 9 and 45/46/76 add the tests and mutants. The same goes for `xdom2nd`, which pushed duplicate attributes once one was missing.
- Step 3: a missing number counts as 0, not the old `getscal`'s -999, which made a rect without `stroke-width` clickable from 999 pixels away. Every diagram the old app wrote has `stroke-width`.
- Step 3: no read-only full-SVG pane. In its place, an **edit** button on the open page's tree row opens the page file in the editor, and gram reloads the page on each save. The node edit modal becomes **Enter** (the external editor), its Done button **Esc**, and the mode toolbar the **0–9** keys and the HUD. The START button is skipped: gram loads the page on open. Selection colors are drawn, never written into the nodes, so the old `cacheColor` isn't needed.
- Step 4: the old `sortSvgNodes` moved text to the front of the node array, which also changed the order of the saved file. gram applies "text first" in hit testing only (`hit-test.sh`), as the steps 0–2 entry asked; the document and the file keep their order.
- Step 4: text click boxes stay on the later `StartEndFrame.FromText` widths (the `CLAUDE.md` rule). Step 4's `12 * length` and step 5's `10 * length` (TDDTEST1 FIX) aren't replayed; step 5 ports TDD TEST 1 against the boxes gram has.
- Edit modes (step 44b, a new feature): plain Enter will stop mapping. Until 44b, Enter maps as the old modal did. JS tests that rely on the map (such as step 5's TDD TEST 0, a rect edit moving its labels) are ported against map mode, and get the map-mode key once 44b exists.
- Step 3: `Node.parent` and keeping shape-less elements out of the R-tree are groundwork for selecting `<g>` groups (step 4a).
- Step 4a, `<g>` groups (a new feature, not in the history): the old app was flat and never read `<g>`. The v0.3 branch's CT/63 (act.svg@19ef414) planned groups as `class="gx-name"` with `Alt-x g` and `Alt-x u` commands, and kept `<g>` for embedding; it was never built (no code uses `gx-`), so nothing in the replay clashes. gram reads `<g>` because other tools write it. Later steps that act on a selection work on its shapes (see `CLAUDE.md`). `map` doesn't move a `line` yet: the line pairs arrive with TDDTEST4. Click boxes ignore a `stroke-width` a shape takes from its `<g>`.
- Step 54 (gram-www@10fa0f8, the book mockup) comes before step 3, out of date order. The folder tree and per-page state are what every later step builds on: selection, the editor process, undo and the save path all live on a `Page`, so building them first saves retrofitting steps 3–53 onto a one-file app. The mockup doesn't depend on any earlier step: its dropdowns become the tree, and its `*` (unsaved changes) becomes `Page.dirty`, which nothing sets until step 3 edits a node. Its PHP login, title and font changes are web-only.
- Steps 0–2: CI comes before its paired step (15), as an agreed exception to pairing, because the pre-parity commit already has tests. `.github/workflows/rust.yml` mirrors everkeep's: it checks out gram and orc side by side (`../orc`), then runs `./test.sh` and `tests/mutate.sh`.
- Steps 0–2: three samples (`diagrams/act (15).svg`, `act(1).svg`, `act(2).svg`) are truncated: each stops right after the first `stroke="` or `fill="` whose value was a hex color. The old "save to file" button (`js/xml-buttons.js`, step 16) built `'data:image/svg+xml,' + encodeURI(xml)`, and `encodeURI` leaves `#` alone, so the browser took the first `#` as the start of a URL fragment and saved only what came before it. The rest is lost. gram opens each as a page showing the parse error instead of the drawing, as a browser would, and keeps running. At step 16, gram writes the file directly, so the bug doesn't carry over; note it in that step's commit body.
- Steps 33 and 36: no diagram command language. The old node command box (CT/49: `setx 100; incx 5; setw 80` run on the node being edited) didn't work well in use, and a command language general enough to script across diagrams that differ a lot (such as padding every node by 4 px) would be a different language from the one CT/49 built. So both steps are skipped, with no commit: TDD TEST 56 (the node-command one; step 35's TDD TEST 56 is the node-drawing branch's rect resize and is ported) and 59–67 aren't ported, and their `TDDTEST N FTR` markers get no mutants. What the commands did is covered by the external editor (exact values) and step 44b's map, align and center keys. The vertex helpers from step 36 (`js/node-vertex.js`) are ported at step 38 instead. A minibuffer for a few named commands is a different thing and does come (step 44a).
- Step 44a, the minibuffer (a new feature): the v0.3 branch (act.svg@19ef414, step 44) planned an Emacs-style `Alt-x` minibuffer for CT/63's `group`/`ungroup`, but built only a key hook that shows "Alt-x". gram builds it, one line, keyboard only, with terminal-Emacs keys, as the way into actions that need a name or are used too rarely to earn a key: a few keys open further editing (the minibuffer or the external editor) instead of a key for everything, and a command used a lot can get its own key later. It is the one exception to "no text-editing widgets": it runs commands and never edits SVG text. It isn't the command language steps 33 and 36 dropped: commands act on the selection, with no scripting. It comes before centering (44b) and the group and ungroup commands (44c).
- Steps 32 and 38: no decision-node sizing. CT/47 (4S DECISION ND RESIZE, act.svg@5d7d83a) and CT/48 (6S DECISION NODE, v0.3) wanted a decision node drawn large enough to hold its question: a drag would stretch the diamond, and later make a 6-sided hexagon as its own shape. CT/47 cites PlantUML's activity-diagram docs (the `if (Graphviz installed?)` example): PlantUML puts the question inside the node and stretches it into a hexagon. Neither was built (only stubs and `todo` comments, still there in gram-www). gram keeps the standard UML decision node: a small diamond, with the conditions as guards on its outgoing edges (`[yes]`, `[no]`). That already says everything the hexagon does, and the standard diamond is the one readers recognize. CT/47's own final scope, resizing the 4-sided diamond by dragging its corners, isn't planned either: tools whose decision nodes look more polished draw them larger, but at a fixed standard size, not dragged out; and a corner of a diamond that small is hard to grab. Picking that standard size is the rest of CT/58 (one click in mode 5 places a standard-sized decision node), still open; its pin half is step 35a. So the stubs and `todo`s aren't ported.
- Step 35a, click-placed pins (a new feature): CT/58 (DECIS./RECT ND CLCK SZ, v0.3) asked for one click in rect mode to make a rect "large enough to match what's expected for a Pin (object node)", and one click in mode 5 a standard-sized decision node. It was never built: a click in rect mode made a 3×3 rect from step 35 on, even in gram-www. gram builds the pin half right after drag-to-draw (step 35) arrives, at the 15×15 the "pins" palette used, for diagrams with many pins; from step 55a on it is the `activity` palette's rect slot that does it. The decision-node half waits for a standard size to be picked (see the steps 32 and 38 entry).
- Step 55a, palettes as SVG files (a new feature): the history never planned a palette you make yourself. Step 21's add-on palettes were fixed example pages (`?template=pins`); CT/69 and CT/75 (v0.4) planned built-in palettes for activity, ER, game flow and story plot, switched with up/down arrows; step 53 built the start of it, each palette's button icons loaded from `buttonbar-buttons/<palette>/<theme>.xml` (one small SVG per button), but the palette list was fixed and every button still only set mode 1–9 or 0. gram goes further: a palette is one SVG file whose `gram-slot` rects hold the stamps, so the user draws, edits and saves palettes with gram itself. Three ship (`activity`, `class-erd`, `game-flow`, which is CT/71 and step 53's Game flow theme); the user's live in `~/.gram/palettes` (or `$GRAM_HOME`). Per-folder palettes were considered and left out: a stamp that is only there in some folders would be frustrating. It comes after save (55) so the bar can save a palette back to its file. The built-in modes 1–9 move into the `activity` palette there (and step 51's game-flow node into `game-flow`), with the earlier tests kept passing against it; that refactor is most of the step's cost.
- Step 5a, undo, redo and select all (CT/56): the v0.3 branch planned Ctrl-Z/Ctrl-Y as an in-memory undo stack and Ctrl-A as select all; CT/62 created `js/xml-hist.js` for it, but the file stayed empty, and nothing in any repo ever had undo. The same wish is act.svg issues #27 (CTRL-A) and #31 (CTRL-Z: "implement undo stack. (also look into undo trees)"), both still open. Undo is a plain stack, not a tree: a tree only helps after undoing and then making a new change, and needs a way to see and choose its branches; git keeps older versions. If losing redo that way ever costs work, keep the cleared states in a time-ordered list (as Vim's `g-` walks them) behind a minibuffer command, with no tree view. gram builds it right after line mode, out of date order, because edits and drawing already change pages and every later step (move, delete, paste, group and ungroup, multi-node edits) can change a lot at once. Built early, each later step only pushes a snapshot for its own change and tests that it undoes.
- CT/57 (XML CREATE ND SHORTCUT, v0.3): keys to insert `<rect>`, `<text>` and the like while typing in the full-XML textarea. Never built, and not planned: gram has no XML pane, and inserting elements while editing the file is the external editor's job (Emacs snippets, for example).
- CT/70 (STABLE 0.3 MERGE, v0.4): v0.3 was never merged into main because a smoke test found it unstable, so v0.4 was to bring in v0.3's refactors (`node-clip`, `node-sel`, `node-del`) and leave the experimental ones (`xmlflow`). Nothing to do: the trunk replays v0.3 (steps 43–46) before v0.4 anyway. Its warning stands: at steps 43–46, watch for behavior the instability may have broken, and port what the tests show.
- CT/73 (NS-CLONE CLI LAUNCH, v0.4): launch the web app from the shell as `act-svg`, with `act_action=version` and `act_action=test`. gram is already a command (`gram <dir>`) and `./test.sh` runs its tests, so only the version is new: step 49a.
- CT/76 (FIX TESTS, v0.4): TDD TEST 10 passed but logged a browser error. Web-only as such; step 7 checks the same path when it ports TDD TEST 10.
- act.svg GitHub issues (#1–#33, all left open, so their state says nothing): each is either done in a commit the replay ports, a "won't implement" (#3, #15), an epic label (#1, #25), or accounted for here: #26 at step 44b, #27 and #31 at step 5a, #28 (web-only) at step 30. #12–#14 and #29 are merged pull requests. #32 (snapping to other nodes) was never built; it is step 40a. #23 is step 20 and #30 step 40, whose commits name CT/51 instead. CT/67 (v0.0, arrow-key moves) and CT/68 (v0.1, click and drag) are epic labels added later in v0.4's `doc/changeboard/versions`; the replay ports their work.
- CT/59, CT/60, CT/66 (v0.3): CT/59's delete is Backspace on the selection (step 19), not a delete mode that removes whatever a rect select caught; its red rectangle and "x" cursor go with the mode. CT/60's letter-key modes aren't ported as keys (step 44): action nodes, object nodes and connectors come as palette stamps (55a), and swimlanes as rects snapped to the page edges (40b) with widths made equal by align (44b). CT/66 gets a Rust test at step 45, and its third problem a selection count in the HUD.
